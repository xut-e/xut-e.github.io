La mayoría de las técnicas de movimiento lateral que hemos presentado requiere puertos específicos para estar disponibles para un atacante. En las redes del mundo real, los administradores pueden tener bloqueados algunos de estos puertos por motivos de seguridad o haber implementado segmentación a lo largo de la red, impidiendo que alcances puertos SMB, RDP, WinRM o RPC.

Para sobrepasar estas restricciones, podemos usar técnicas de redireccionamiento de puertos las cuales consisten en usar cualquier host comprometido como caja de salto para pivotar a otros hosts. Se espera que algunas máquinas tengan más permisos de red que otras, ya que todos los roles en un negocio tienen necesidades diferentes en términos de lo que requieren los servicios de red en el trabajo diario.

-------------------------------------
<h2>Túnel SSH</2>
El primer protocolo que veremos será SSH, ya que tiene funcionalidades implementadas para realizar port forwarding a través de una funcionalidad llamada **SSH Tunneling**. Aunque SSH solía ser un protocolo asociado a sistemas Linux, Windows ahora sale con el cliente SSH por defecto, por lo que puedes esperar encontrarlo en múltiples sistemas hoy en día.

La tunelación SSH puede ser usada de formas diferentes para redireccionar puertos a través de una conexión SSH. Para explicar cada caso, vamos a asumir un escenario donde hemos ganado control sobre la máquina PC-1 (no necesita ser como administrador) y queremos usarla como pivote para acceder a un puerto en otra máquina a la que no podemos conectarnos directamente. Comenzaremos un túnel desde la máquina PC-1 actuando como cliente SSH hacia la máquina del atacante la cual actuará como servidor SSH. La razón de hacerlo así es que normalmente encontrarás clientes SSH en las máquinas Windows, pero no servidores SSH.

![[Pasted image 20260915090821.png]]

Como estaremos realizando una conexión de vuelta a nuestra máquina de atacante, queremos crear un usuario en ella sin acceso a ninguna consola para la tunelación:

```bash
useradd tunneluser -m -d /home/tunneluser -s /bin/true
passwd tunneluser
```

Dependiendo de tus necesidades, el túnel SSH puede ser usado para hacer una redirección de puertos local o remota. Vamos a ver cada caso.

-----------------------------------------
<h2>Port Forwarding Remoto SSH</h2>
En nuestro ejemplo, vamos a asumir que las políticas del firewall bloquean la máquina del atacante de acceder directamente al puerto 3389 en el servidor. Si el atacante ha comprometido el PC-1 previamente y este tiene acceso al puerto en cuestión, puede ser usado para pivotar hacia dicho puerto mediante redireccionamiento de puertos.

Como resultado, un puerto será abierto en la máquina del atacante que puede ser usado para conectarse al puerto 3389 en el servidor a través de un túnel SSH. El PC-1, hará de proxy de la conexión por lo que el servidor verá que el tráfico venía de PC-1.

![[Pasted image 20260915091653.png]]

Una pregunta válida sería que por qué necesitamos port forwarding si ya hemos comprometido la máquina PC-1 y podemos ejecutar una sesión RDP desde ahí. Bien, no siempre tendremos acceso  a la GUI, quizá sólo tenemos acceso a la línea de comandos.

Referente a la imagen anterior, para redireccionar el puerto 3389 del servidor a nuestra máquina, podemos usar el siguiente comando en el PC-1:

```bash
ssh tunneluser@1.1.1.1 -R 3389:3.3.3.3:3389 -N
```

Esto establecerá una sesión desde el PC-1 a `1.1.1.1` usando el usuario `tunneluser`.

Como `tunneluser` no tiene permitido ejecutar una shell en el PC del atacante, necesitamos ejecutar el comando `ssh` con el switch `-N` para prevenir al cliente de pedir una o la conexión terminará inmediatamente. El switch `-R` es usado para pedir una redirección remota de puertos, y la sintaxis requiere que indiquemos primero el puerto que abriremos en el servidor SSH seguido de la IP y el puerto al que redirigiremos. Los puertos no tienen por qué coincidir aunque lo hagan en el ejemplo.

El comando por sí mismo no mostrará nada, pero el túnel será hecho. Cuando queramos, podemos cerrar el túnel presionando `CTRL+C`.

Una vez el túnel esté funcionando, podemos ir a la máquina del atacante y hacer RDP al puerto redireccionado para acceder al servidor:

```bash
xfreerdp3 /v:127.0.0.1 /u:MyUser /p:MyPassword +dynamic-resolution
```

<h2>Port Forwarding Local SSH</h2>
Nos permite coger un puerto del servidor SSH y meterlo en nuestro cliente. En nuestro escenario, esto podría ser usado para tomar cualquier servicio disponible en nuestra máquina y hacerlo disponible a través de un puerto en PC-1. De esa forma, cualquier host no pueda conectarse directamente al PC del atacante pero sí al PC-1 podrá ahora acceder a los servicios del atacante.

Usar este tipo de redireccionamiento nos permite ejecutar reverse shells desde hosts que normalmente no serían capaces de conectarse a nosotros o simplemente hacer cualquier servicio disponible a las máquinas que no tienen conexión directa con nosotros.

![[Pasted image 20260915102954.png]]

Para redireccionar el puerto 80 desde la máquina del atacante y hacerla disponible a PC-1, podemos usar el siguiente comando en PC-1:

```bash
ssh tunneluser@1.1.1.1 -L *:80:127.0.0.1:80 -N
```

La estructura del comando es similar a la usada en la redirección remota pero usa `-L` en lugar de `-R`. Esta opción requiere que indiquemos un socket local usado por PC-1 para recibir conexiones (`*:80`) y el socket remoto para conectarse desde la perspectiva del atacante (`127.0.0.1:80`).

Como estamos abriendo un nuevo puerto en PC-1, puede que necesitemos añadir una regla de firewall para permitir conexiones entrantes (con `dir=in`). Se requieren permisos administrativos:

```cmd
netsh advfirewall firewall add rule name="Open Port 80" dir=in action=allow protocol=TCP localport=80
```

Una vez que el túnel esté activo, cualquier usuario que apunte al PC-1 a `http://2.2.2.2:80` y vean la web publicada por la máquina del atacante.

<h2>Port Forwarding con socat</h2>
En situaciones donde SSH no está disponible, socat puede ser usado para realizar una función similar. Aunque no es tan flexible como SSH, socat permite que redirijas puertos de una manera mucho más simple. Una de las desventajas de usar socat es que necesitas transferirlo al pivote, haciéndolo más detectable que SSH, pero puede valer la pena probar si no existe otra opción.

La sintaxis básica para realizar un port forwarding usando socat es mucho más simple. Si quisiéramos abrir el puerto 1234 en un host y redirigir cualquier conexión que recibamos ahí al puerto 4321 en el host 1.1.1.1, usaríamos el siguiente comando:

```bash
socat TCP4-LISTEN:1234,fork TCP4:1.1.1.1:4321
```

La opción `fork` permite a socat hacer un fork de un nuevo proceso por cada conexión recibida, haciéndolo posible manejar múltiples conexiones sin cerrar. Si no quieres incluirlo, socat se cerrará cuando la primera conexión hecha se finalice.

Volviendo a nuestro ejemplo, si quisiéramos acceder al puerto 3389 en el servidor usando PC-1 como pivote como hicimos con el port forwarding remoto de SSH, podríamos usar el siguiente comando:

```bash
socat TCP4-LISTEN:3389,fork TCP4:3.3.3.3:3389
```

>[!IMPORTANT] Ten en cuenta que `socat` no puede redirigir la conexión directamente a la máquina del atacante como hacía SSH pero abrirá un puerto en PC-1 al que la máquina del atacante se pueda conectar.

![[Pasted image 20260915141354.png]]

Como de manera usual, como un puerto es abierto en el host pivote, puede que necesitemos crear una regla de firewall para permitir las conexiones a dicho puerto:

```cmd
netsh advfirewall firewall add rule name="Open Port 3389" dir=in action=allow protocol=TCP localport=3389
```

Si quisiéramos exponer el puerto 80 de la máquina del atacante para que no fuera alcanzable por el servidor, sólo necesitaríamos ajustar un poco el comando:

```bash
socat TCP4-LISTEN:80,fork TCP4:1.1.1.1:80
```

Como resultado, PC-1 spawneará el puerto 80 y escuchará conexiones para redirigirlas al puerto 80 del atacante:

![[Pasted image 20260915141658.png]]

<h2>Port Forwarding Dinámico y SOCKS</h2>
Mientras que el single port forwarding funciona bastante bien para tareas que requieren acceder a sockets específicos, hay momentos donde puede que necesitemos ejecutar escaneos contra muchos puertos de un host, o incluso muchos puertos a lo largo de muchas máquinas. En esos casos, el redireccionamiento de puertos dinámico nos permite pivotar a través de un host y establecer varias conexiones a una dirección/puerto IP que queramos usando el proxy SOCKS.

Como no queremos depender de que exista un servidor SSH en las máquinas Windows de nuestro objetivo, normalmente usaremos el cliente SSH para establecer un redireccionamiento de puertos dinámico inverso con el siguiente comando:

```bash
ssh tunneluser@1.1.1.1 -R 9050 -N
```

En este caso, el servidor SSH comenzará un proxy SOCKS en el puerto `9050` y redirigirá cualquier petición de conexión a través del túnel SSH, donde finalmente sera proxied por el cliente SSH.

La parte más interesante es que podemos usar cualquier herramienta a través del proxy de SOCKS usando proxychains. Para hacerlo, necesitamos asegurarnos de que proxychains está correctamente configurado para apuntar al mismo puerto usado por SSH por el servidor de proxy SOCKS. El archivo de configuración de proxychains puede ser encontrado en `/etc/proxychains.conf`. Si vamos hasta el final del archivo de configuración, veremos una linea que indica el puerto en uso para el proxy de socks:

```conf
[ProxyList]
socks4  127.0.0.1 9050
```

El puerto por defecto es 9050 pero cualquier puerto funcionará mientras coincida con el usado al establecer el túnel SSH.

Si queremos ahora ejecutar cualquier comando a través del proxy, podemos usar proxychains:

```bash
proxychains curl http://pxeboot.za.tryhackme.com
```
